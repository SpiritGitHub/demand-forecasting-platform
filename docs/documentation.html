Demand Forecasting & Replenishment Platform

Documentation technique — Phases 1-3 : Ingestion, enrichissement, feature engineering et modelisation. Plateforme de prevision de la demande et de recommandation de reapprovisionnement pour le retail.

Python 3.11+ PostgreSQL Pandera Docker MLflow PyTorch XGBoost LightGBM Prophet FastAPI Streamlit Airflow

Ce projet construit un systeme end-to-end capable de predire combien d'unites de chaque produit seront vendues dans chaque magasin durant les 7, 14 et 30 prochains jours, puis de transformer ces previsions en recommandations de reapprovisionnement actionables (quantite a commander, risque de rupture, urgence).

Les tags en surbrillance indiquent les technologies deja implementees dans la Phase 1. Les tags gris correspondent aux phases futures.

3 services :

db (PostgreSQL 15) — Base relationnelle qui stocke les ventes, les magasins, la meteo et les previsions. Le fichier init_db.sql est monte dans /docker-entrypoint-initdb.d/ : Postgres l'execute automatiquement au premier demarrage du conteneur. Le healthcheck avec pg_isready garantit que les services dependants ne demarrent qu'une fois la base prete a accepter des connexions.

pgadmin — Interface web pour explorer les tables et executer des requetes SQL manuellement. Accessible sur localhost:8080. Attend que la base soit healthy avant de demarrer.

mlflow — Serveur de tracking des experiences ML. Utilise PostgreSQL comme backend (les metriques et parametres sont stockes en base, pas dans des fichiers locaux). Les artefacts (modeles serialises) sont stockes dans un volume Docker dedie. Accessible sur localhost:5000.

La syntaxe ${VAR:-default} lit les valeurs du fichier .env avec un fallback si la variable n'est pas definie.

Schema SQL de la base de donnees

scripts/init_db.sql
CREATE TABLE IF NOT EXISTS stores (
    store_id              INTEGER PRIMARY KEY,
    store_type            VARCHAR(10),
    assortment            VARCHAR(10),
    competition_distance  FLOAT,
    competition_open_since_month INTEGER,
    competition_open_since_year  INTEGER,
    promo2                INTEGER,
    promo2_since_week     INTEGER,
    promo2_since_year     INTEGER,
    promo_interval        VARCHAR(100)
);

CREATE TABLE IF NOT EXISTS sales (
    id             SERIAL PRIMARY KEY,
    store_id       INTEGER REFERENCES stores(store_id),
    date           DATE NOT NULL,
    day_of_week    INTEGER,
    sales          INTEGER,
    customers      INTEGER,
    is_open        INTEGER,
    promo          INTEGER,
    state_holiday  VARCHAR(5),
    school_holiday INTEGER
);

CREATE TABLE IF NOT EXISTS weather (
    id               SERIAL PRIMARY KEY,
    store_id         INTEGER REFERENCES stores(store_id),
    date             DATE NOT NULL,
    temperature_mean FLOAT,
    temperature_max  FLOAT,
    temperature_min  FLOAT,
    precipitation    FLOAT,
    wind_speed       FLOAT,
    UNIQUE(store_id, date)
);

CREATE TABLE IF NOT EXISTS forecasts (
    id               SERIAL PRIMARY KEY,
    store_id         INTEGER REFERENCES stores(store_id),
    forecast_date    DATE NOT NULL,
    target_date      DATE NOT NULL,
    horizon          INTEGER,
    model_name       VARCHAR(100),
    predicted_sales  FLOAT,
    confidence_low   FLOAT,
    confidence_high  FLOAT,
    created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_sales_store_date     ON sales(store_id, date);
CREATE INDEX idx_weather_store_date   ON weather(store_id, date);
CREATE INDEX idx_forecasts_store_date ON forecasts(store_id, target_date);

4 tables :

stores — Metadata de chaque magasin : type (a/b/c/d), assortiment, distance du concurrent le plus proche, participation aux promotions recurrentes (promo2). C'est la table de reference, les autres la rejoignent via store_id.

sales — Historique quotidien : ventes, clients, etat d'ouverture, promotion du jour, type de jour ferie. Cle etrangere vers stores. L'index composite (store_id, date) accelere les requetes de series temporelles par magasin — le pattern le plus frequent dans le forecasting.

weather — Meteo quotidienne par magasin. La contrainte UNIQUE(store_id, date) evite les doublons lors des re-executions du pipeline d'enrichissement.

forecasts — Table de sortie pour stocker les previsions generees par les modeles. forecast_date = quand la prevision a ete faite, target_date = le jour predit. Cela permet de suivre la performance des previsions dans le temps (etaient-elles justes ?).

def download_rossmann(output_dir: Path = RAW_DIR) -> Path:
    """Download Rossmann Store Sales dataset from Kaggle."""
    output_dir.mkdir(parents=True, exist_ok=True)
    zip_path = output_dir / "rossmann-store-sales.zip"

    # Idempotence : si train.csv existe deja, on skip
    if (output_dir / "train.csv").exists():
        logger.info("Dataset already downloaded, skipping.")
        return output_dir

    logger.info("Downloading Rossmann dataset from Kaggle...")
    subprocess.run(
        [
            "kaggle", "competitions", "download",
            "-c", "rossmann-store-sales",
            "-p", str(output_dir),
        ],
        check=True,
    )

    # Extraction du ZIP puis suppression de l'archive
    if zip_path.exists():
        logger.info("Extracting archive...")
        with zipfile.ZipFile(zip_path, "r") as zf:
            zf.extractall(output_dir)
        zip_path.unlink()

    return output_dir

Idempotence : la verification if train.csv exists en debut de fonction fait que re-executer le pipeline ne re-telecharge pas les donnees. C'est essentiel pour un pipeline reproductible — on veut pouvoir relancer sans effets de bord.

Le telechargement utilise la CLI Kaggle (subprocess.run avec check=True pour lever une exception si la commande echoue). Le ZIP est extrait en place puis supprime pour ne garder que les CSV utiles (train.csv, store.csv, test.csv).

def load_raw_data(data_dir: Path = RAW_DIR) -> tuple[pd.DataFrame, pd.DataFrame]:
    """Load raw CSV files into DataFrames."""
    train = pd.read_csv(
        data_dir / "train.csv",
        parse_dates=["Date"],          # Convertir en datetime directement
        dtype={"StateHoliday": str},   # Forcer en string (contient '0' et 'a')
        low_memory=False,
    )
    store = pd.read_csv(data_dir / "store.csv")
    logger.info("Loaded train: %s rows, store: %s rows", len(train), len(store))
    return train, store

parse_dates=["Date"] — Pandas parse la colonne Date en datetime64 directement au chargement, ce qui evite de le faire apres et accelere les operations temporelles.

dtype={"StateHoliday": str} — Cette colonne contient a la fois "0" (pas de ferie) et des lettres "a", "b", "c" (types de jours feries). Sans cette indication, Pandas infere un type mixte et emet un avertissement. Forcer le type str resout le probleme a la source.

Deux DataFrames retournes : train contient les ventes quotidiennes (~1M lignes) et store contient les metadonnees des 1115 magasins. Ils seront fusionnes dans clean_data().

def clean_data(train: pd.DataFrame, store: pd.DataFrame) -> pd.DataFrame:
    """Merge and clean raw data."""
    # 1. Jointure : enrichir chaque vente avec les infos du magasin
    df = train.merge(store, on="Store", how="left")

    # 2. Normalisation des noms de colonnes : CamelCase → snake_case
    df.columns = [c.lower() for c in df.columns]
    df = df.rename(columns={
        "store": "store_id",
        "dayofweek": "day_of_week",
        "stateholiday": "state_holiday",
        "schoolholiday": "school_holiday",
        "competitiondistance": "competition_distance",
        "competitionopensincemonth": "competition_open_since_month",
        "competitionopensinceyear": "competition_open_since_year",
        "storetype": "store_type",
        "promo2sinceweek": "promo2_since_week",
        "promo2sinceyear": "promo2_since_year",
        "promointerval": "promo_interval",
    })

    # 3. Filtrage : ne garder que les jours ouverts avec des ventes
    df = df[df["is_open"] == 1].copy()
    df = df[df["sales"] > 0].copy()

    # 4. Tri chronologique par magasin
    df = df.sort_values(["store_id", "date"]).reset_index(drop=True)

    return df

4 etapes de nettoyage :

1. Jointure LEFT — Chaque ligne de vente recoit les colonnes du magasin correspondant. how="left" conserve toutes les ventes meme si un magasin manquait dans store.csv (securite).

2. Renommage snake_case — Convention Python standard. Les noms originaux Kaggle (DayOfWeek, CompetitionDistance) deviennent day_of_week, competition_distance. Cela aligne aussi les noms avec les colonnes PostgreSQL.

3. Filtrage — On exclut les jours ou le magasin etait ferme (is_open == 0) et les ventes nulles. Un magasin ferme a 0 ventes par definition, pas par manque de demande. Garder ces lignes fausserait les modeles en leur apprenant que certains jours ont naturellement 0 ventes.

4. Tri — L'ordre (store_id, date) est indispensable pour les operations de series temporelles (lags, rolling means). .copy() evite les SettingWithCopyWarning de Pandas.

def insert_stores(store: pd.DataFrame, engine) -> None:
    """Insert store data into PostgreSQL."""
    store_clean = store.copy()
    store_clean.columns = [c.lower() for c in store_clean.columns]
    store_clean = store_clean.rename(columns={...})  # meme mapping que clean_data

    cols = [
        "store_id", "store_type", "assortment", "competition_distance",
        "competition_open_since_month", "competition_open_since_year",
        "promo2", "promo2_since_week", "promo2_since_year", "promo_interval",
    ]
    store_clean = store_clean[cols]
    store_clean.to_sql("stores", engine, if_exists="replace", index=False)


def insert_sales(df: pd.DataFrame, engine) -> None:
    """Insert sales data into PostgreSQL."""
    cols = [
        "store_id", "date", "day_of_week", "sales", "customers",
        "is_open", "promo", "state_holiday", "school_holiday",
    ]
    sales_df = df[cols].copy()
    sales_df.to_sql("sales", engine, if_exists="replace", index=False)

to_sql() de Pandas ecrit un DataFrame entier dans une table PostgreSQL. if_exists="replace" supprime et recree la table a chaque execution — c'est voulu pour la phase de developpement (pipeline idempotent). En production, on utiliserait "append" avec une logique d'upsert.

La selection explicite des colonnes (cols = [...]) garantit qu'on n'insere que les colonnes attendues par le schema SQL, dans le bon ordre. C'est aussi une forme de documentation : on voit exactement ce qui entre dans chaque table.

def run_ingestion() -> pd.DataFrame:
    """Full ingestion pipeline: download, clean, insert into DB."""
    # Etape 1 : telecharger si necessaire
    download_rossmann()

    # Etape 2 : charger les CSV en memoire
    train, store = load_raw_data()

    # Etape 3 : nettoyer et fusionner
    df = clean_data(train, store)

    # Etape 4 : preparer la base (drop cascade puis recreer)
    engine = create_engine(DATABASE_URL)
    with engine.begin() as conn:
        conn.execute(text("DROP TABLE IF EXISTS forecasts"))
        conn.execute(text("DROP TABLE IF EXISTS weather"))
        conn.execute(text("DROP TABLE IF EXISTS sales"))
        conn.execute(text("DROP TABLE IF EXISTS stores"))

    # Etape 5 : inserer dans PostgreSQL
    insert_stores(store, engine)
    insert_sales(df, engine)

    # Etape 6 : sauvegarder en Parquet pour usage offline
    df.to_parquet(RAW_DIR / "rossmann_clean.parquet", index=False)

    return df


if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO)
    run_ingestion()

Orchestration en 6 etapes : telecharger, charger, nettoyer, preparer la base, inserer, sauvegarder.

Les DROP TABLE sont executes dans l'ordre inverse des dependances (foreign keys) : forecasts et weather referencent sales et stores, donc ils doivent etre supprimes en premier. C'est un pattern classique pour les pipelines de reinitialisation.

Double sortie : les donnees vont a la fois dans PostgreSQL (pour les requetes et le dashboard) et dans un fichier Parquet (pour le travail en notebook et le feature engineering). Parquet est un format colonnaire binaire, beaucoup plus rapide a lire que CSV (~10x) et plus compact.

Le bloc if __name__ == "__main__" permet d'executer le pipeline directement : 

python -m src.data.ingestion

Enrichissement des donnees

Le module src/data/enrichment.py ajoute des variables externes qui capturent des facteurs influencant les ventes mais absents du dataset Rossmann : les jours feries nationaux, les patterns calendaires, et la meteo.

def add_holiday_features(df: pd.DataFrame) -> pd.DataFrame:
    """Add German holiday flags and distance to nearest holiday."""
    # Generer tous les jours feries allemands pour la periode
    years = range(df["date"].dt.year.min(), df["date"].dt.year.max() + 1)
    de_holidays = holidays.Germany(years=years)

    holiday_dates = sorted(de_holidays.keys())

    # Feature binaire : est-ce un jour ferie ?
    df["is_holiday"] = df["date"].dt.date.isin(de_holidays).astype(int)

    # Nom du jour ferie (vide si ce n'en est pas un)
    df["holiday_name"] = df["date"].dt.date.map(
        lambda d: de_holidays.get(d, "")
    )

    # Distance en jours au jour ferie le plus proche
    holiday_series = pd.Series(holiday_dates)

    def days_to_nearest_holiday(d: date) -> int:
        idx = holiday_series.searchsorted(d)
        candidates = []
        if idx < len(holiday_series):
            candidates.append(abs((holiday_series.iloc[idx] - d).days))
        if idx > 0:
            candidates.append(abs((d - holiday_series.iloc[idx - 1]).days))
        return min(candidates) if candidates else 999

    df["days_to_holiday"] = df["date"].dt.date.map(days_to_nearest_holiday)

    return df

3 features generees :

is_holiday (0/1) — Indique si le jour est un jour ferie allemand. La librairie holidays connait tous les jours feries nationaux et regionaux.

holiday_name — Le nom du jour ferie (par ex. "Weihnachten" pour Noel). Utile pour l'analyse exploratoire ; pas directement utilisable comme feature numerique.

days_to_holiday — Nombre de jours jusqu'au ferie le plus proche (avant ou apres). C'est la feature la plus interessante pour le ML : les ventes augmentent souvent dans les jours precedant un ferie (effet d'anticipation des achats). L'algorithme utilise searchsorted (recherche binaire O(log n)) pour trouver efficacement le ferie le plus proche dans la liste triee.

def add_calendar_features(df: pd.DataFrame) -> pd.DataFrame:
    """Add calendar-based features."""
    dt = df["date"].dt

    df["month"]          = dt.month
    df["week_of_year"]   = dt.isocalendar().week.astype(int)
    df["quarter"]        = dt.quarter
    df["year"]           = dt.year
    df["is_weekend"]     = (dt.dayofweek >= 5).astype(int)
    df["is_month_start"] = dt.is_month_start.astype(int)
    df["is_month_end"]   = dt.is_month_end.astype(int)
    df["day_of_month"]   = dt.day

    return df

8 features calendaires extraites de la colonne date. Chacune capture un cycle temporel different qui influence les ventes :

month (1-12) — Saisonnalite annuelle. Decembre a un profil de ventes tres different de fevrier.

week_of_year (1-53) — Plus granulaire que le mois. dt.isocalendar().week utilise le standard ISO 8601 (semaine 1 = celle contenant le premier jeudi).

is_weekend (0/1) — Les patterns d'achat du samedi/dimanche different radicalement des jours de semaine. dayofweek >= 5 correspond a samedi (5) et dimanche (6).

is_month_start / is_month_end — Effet de paie : les ventes augmentent souvent en debut de mois (salaires verses) et en fin de mois (achats de derniere minute).

L'accesseur .dt de Pandas permet d'extraire ces attributs vectoriellement sur toute la colonne sans boucle Python — beaucoup plus rapide.

fetch_weather_data()

src/data/enrichment.py — lignes 76-116
def fetch_weather_data(
    latitude: float = 51.5,
    longitude: float = 10.5,
    start_date: str = "2013-01-01",
    end_date: str = "2015-07-31",
) -> pd.DataFrame:
    """Fetch historical weather from Open-Meteo API (free, no key)."""
    EXTERNAL_DIR.mkdir(parents=True, exist_ok=True)
    cache_path = EXTERNAL_DIR / "weather_germany.parquet"

    # Cache local pour eviter de rappeler l'API
    if cache_path.exists():
        return pd.read_parquet(cache_path)

    url = "https://archive-api.open-meteo.com/v1/archive"
    params = {
        "latitude": latitude,
        "longitude": longitude,
        "start_date": start_date,
        "end_date": end_date,
        "daily": "temperature_2m_mean,temperature_2m_max,"
                 "temperature_2m_min,precipitation_sum,"
                 "wind_speed_10m_max",
        "timezone": "Europe/Berlin",
    }

    resp = requests.get(url, params=params, timeout=30)
    resp.raise_for_status()
    data = resp.json()

    weather = pd.DataFrame({
        "date":             pd.to_datetime(data["daily"]["time"]),
        "temperature_mean": data["daily"]["temperature_2m_mean"],
        "temperature_max":  data["daily"]["temperature_2m_max"],
        "temperature_min":  data["daily"]["temperature_2m_min"],
        "precipitation":    data["daily"]["precipitation_sum"],
        "wind_speed":       data["daily"]["wind_speed_10m_max"],
    })

    # Sauvegarder en cache
    weather.to_parquet(cache_path, index=False)
    return weather

Open-Meteo Archive API — API gratuite, sans cle, qui fournit la meteo historique pour n'importe quelle coordonnee GPS. Les coordonnees par defaut (51.5, 10.5) correspondent au centre geographique de l'Allemagne.

5 variables meteo : temperature moyenne/max/min, precipitations cumulees, vitesse max du vent. Ce sont les facteurs meteo les plus correles au trafic en magasin (les gens sortent moins quand il pleut ou fait tres froid).

Cache Parquet — Apres le premier appel API, les donnees sont sauvegardees localement. Les executions suivantes lisent le cache sans toucher au reseau. C'est important pour la reproductibilite et pour ne pas surcharger une API gratuite.

Limitation connue : un seul point GPS pour toute l'Allemagne. En production, on utiliserait les coordonnees de chaque magasin pour une meteo localisee. Pour un projet portfolio, la meteo nationale suffit a capturer les grandes tendances.

def enrich_with_weather(df: pd.DataFrame) -> pd.DataFrame:
    """Merge weather data into the sales DataFrame."""
    start = df["date"].min().strftime("%Y-%m-%d")
    end   = df["date"].max().strftime("%Y-%m-%d")

    weather = fetch_weather_data(start_date=start, end_date=end)
    df = df.merge(weather, on="date", how="left")

    # Feature derivee : jour de pluie (> 1mm)
    df["is_rainy"] = (df["precipitation"].fillna(0) > 1.0).astype(int)

    return df


def run_enrichment(df: pd.DataFrame) -> pd.DataFrame:
    """Run all enrichment steps."""
    df = add_calendar_features(df)
    df = add_holiday_features(df)
    df = enrich_with_weather(df)
    return df

Verification de la continuite des dates

src/data/validation.py — lignes 52-71
def check_date_continuity(df: pd.DataFrame) -> dict:
    """Check for gaps in date sequences per store."""
    issues = {}

    for store_id, group in df.groupby("store_id"):
        dates = group["date"].sort_values()

        # Generer toutes les dates attendues entre min et max
        expected = pd.date_range(dates.min(), dates.max(), freq="D")

        # Les dates manquantes = attendues - presentes
        missing = set(expected) - set(dates)

        if missing:
            issues[store_id] = sorted(missing)

    if issues:
        total_gaps = sum(len(v) for v in issues.values())
        logger.warning(
            "Date gaps found in %d stores (%d total missing days)",
            len(issues), total_gaps,
        )
    else:
        logger.info("No date gaps found")

    return issues

Pourquoi c'est critique pour le forecasting : les modeles de series temporelles (LSTM, TFT, et meme les lags features) supposent que les dates sont continues. Un trou de 3 jours dans les donnees d'un magasin fausserait le calcul sales_lag_7 (le lag pointerait sur le mauvais jour).

L'algorithme est simple : pour chaque magasin, generer la sequence complete de dates entre le premier et le dernier jour, puis comparer avec les dates reellement presentes. La difference = les jours manquants.

Les trous sont attendus dans Rossmann (magasins fermes le dimanche, renovations...). Cette fonction ne les corrige pas, elle les detecte. La correction (interpolation, imputation, ou exclusion) sera geree dans le feature engineering (Phase 2).

Feature Engineering

Le module src/features/engineering.py construit les features ML a partir du dataset enrichi. Toutes les features temporelles (lags, rolling) sont calculees par magasin et decalees d'un jour (shift(1)) pour eviter le data leakage.

Features de lag et rolling

src/features/engineering.py — add_lag_features, add_rolling_features, add_ewm_features
def add_lag_features(df, target="sales", lags=None):
    if lags is None:
        lags = [7, 14, 28]
    for lag in lags:
        col = f"{target}_lag_{lag}"
        df[col] = df.groupby("store_id")[target].shift(lag)
    return df

def add_rolling_features(df, target="sales", windows=None):
    if windows is None:
        windows = [7, 14, 28]
    grouped = df.groupby("store_id")[target]
    for w in windows:
        shifted = grouped.shift(1)           # exclure le jour courant
        rolling = shifted.rolling(window=w, min_periods=w)
        df[f"{target}_rolling_mean_{w}"] = rolling.mean()
        if w == 7:
            df[f"{target}_rolling_std_{w}"] = rolling.std()
    return df

def add_ewm_features(df, target="sales", span=7):
    shifted = df.groupby("store_id")[target].shift(1)
    df[f"{target}_ewm_{span}"] = shifted.ewm(span=span, min_periods=span).mean()
    return df

def add_trend_features(df, target="sales"):
    # Momentum : difference entre moyenne courte et longue
    if f"{target}_rolling_mean_7" in df.columns:
        df[f"{target}_trend"] = (
            df[f"{target}_rolling_mean_7"] - df[f"{target}_rolling_mean_28"]
        )
    return df

7 features temporelles generees :

Lags (3 features) — sales_lag_7, sales_lag_14, sales_lag_28 : les ventes du meme magasin il y a 7, 14, et 28 jours. C'est l'information la plus predictive : les ventes de la semaine derniere sont un excellent indicateur des ventes de cette semaine.

Rolling (4 features) — Moyenne mobile sur 7/14/28 jours et ecart-type sur 7 jours. Le shift(1) est critique : sans lui, la moyenne inclurait les ventes du jour qu'on essaie de predire. min_periods=w garantit qu'on ne calcule la moyenne que quand on a suffisamment de donnees (les premiers jours produisent des NaN).

EWM — Moyenne mobile exponentielle (span=7). Donne plus de poids aux jours recents, ce qui capture mieux les changements de tendance que la moyenne simple.

Trend — rolling_mean_7 - rolling_mean_28. Un trend positif signifie que les ventes recentes sont au-dessus de la moyenne long terme (acceleration).

Features promo et competition

src/features/engineering.py — add_promo_features, add_competition_features
def add_promo_features(df):
    # Nombre de jours consecutifs de promo
    promo_groups = df.groupby("store_id")["promo"]
    df["promo_duration"] = promo_groups.transform(
        lambda s: s.groupby((s != s.shift()).cumsum()).cumcount() + 1
    )
    df.loc[df["promo"] == 0, "promo_duration"] = 0
    return df

def add_competition_features(df):
    # Log de la distance (reduit l'asymetrie)
    median_dist = df["competition_distance"].median()
    df["competition_distance"] = df["competition_distance"].fillna(median_dist)
    df["competition_distance_log"] = np.log1p(df["competition_distance"])

    # Nombre de mois depuis l'ouverture du concurrent
    comp_year = df["competition_open_since_year"].fillna(0).astype(int)
    comp_month = df["competition_open_since_month"].fillna(0).astype(int)
    df["competition_open_months"] = (
        (df["date"].dt.year - comp_year) * 12
        + (df["date"].dt.month - comp_month)
    ).clip(lower=0)
    return df

promo_duration — Compte le nombre de jours consecutifs de promotion. L'algorithme utilise cumsum() sur les changements d'etat (0→1 ou 1→0) pour identifier chaque "bloc" de promo, puis cumcount() pour compter les jours dans chaque bloc. La duree est remise a 0 les jours sans promo. Cette feature capture l'effet d'usure des promos : le lift diminue apres plusieurs jours.

competition_distance_log — log(1 + distance) reduit l'asymetrie de la distribution (quelques magasins ont des concurrents tres loin). Les valeurs manquantes sont imputees par la mediane.

competition_open_months — Depuis combien de mois le concurrent le plus proche est ouvert. Un nouveau concurrent peut impacter les ventes differemment qu'un concurrent etabli.

Interactions et encodage

src/features/engineering.py — add_store_encoding, add_interaction_features
def add_store_encoding(df):
    type_map = {"a": 1, "b": 2, "c": 3, "d": 4}
    assort_map = {"a": 1, "b": 2, "c": 3}
    df["store_type_enc"] = df["store_type"].str.lower().map(type_map).fillna(0)
    df["assortment_enc"] = df["assortment"].str.lower().map(assort_map).fillna(0)
    return df

def add_interaction_features(df):
    df["promo_x_weekend"]      = df["promo"] * df["is_weekend"]
    df["promo_x_holiday"]      = df["promo"] * df["is_holiday"]
    df["holiday_x_store_type"]  = df["is_holiday"] * df["store_type_enc"]
    df["dow_x_promo"]          = df["day_of_week"] * df["promo"]
    return df

Encodage ordinal — Les types de magasin (a/b/c/d) et d'assortiment (a/b/c) sont convertis en entiers. L'encodage ordinal est suffisant pour les modeles a base d'arbres (XGBoost, LightGBM) qui n'assument pas de relation lineaire entre les categories.

Features d'interaction (4 features) — Le produit de deux features binaires capture l'effet combine. Par exemple, promo_x_weekend = 1 uniquement quand il y a promo ET c'est le weekend. Cela permet au modele de capturer des effets non-lineaires sans avoir a les decouvrir lui-meme.

Agregats par magasin

src/features/engineering.py — add_store_aggregates, add_dow_profile
def add_store_aggregates(df, train_end_date=None):
    # Utiliser uniquement les donnees d'entrainement pour eviter le leakage
    if train_end_date is not None:
        ref = df[df["date"] <= pd.Timestamp(train_end_date)]
    else:
        ref = df

    store_stats = ref.groupby("store_id")["sales"].agg(
        store_mean_sales="mean",
        store_median_sales="median",
        store_std_sales="std",
    ).reset_index()

    df = df.merge(store_stats, on="store_id", how="left")
    return df

def add_dow_profile(df, train_end_date=None):
    # Profil de ventes par (magasin, jour de la semaine)
    if train_end_date is not None:
        ref = df[df["date"] <= pd.Timestamp(train_end_date)]
    else:
        ref = df

    store_dow = ref.groupby(["store_id", "day_of_week"])["sales"].mean().reset_index()
    store_dow = store_dow.rename(columns={"sales": "store_dow_mean_sales"})
    df = df.merge(store_dow, on=["store_id", "day_of_week"], how="left")

    # Ratio : ventes du jour / moyenne globale du magasin
    store_mean = ref.groupby("store_id")["sales"].mean()
    df["store_dow_ratio"] = df["store_dow_mean_sales"] / df["store_id"].map(store_mean)
    return df

Anti-leakage via train_end_date — Les agregats (moyenne, mediane, std par magasin) sont calcules uniquement sur les donnees d'entrainement. Sans cette precaution, les features contiendraient de l'information du futur et le modele aurait des scores artificiellement bons en validation mais mauvais en production.

store_mean_sales / store_median_sales / store_std_sales — Capturent le "niveau" de chaque magasin. Un magasin qui vend en moyenne 8000 par jour a un profil tres different d'un magasin a 3000. Ces features permettent au modele de situer chaque magasin.

store_dow_mean_sales — Ventes moyennes du magasin X le lundi, le mardi, etc. C'est une feature tres puissante car chaque magasin a son propre profil hebdomadaire (certains vendent beaucoup le samedi, d'autres non).

store_dow_ratio — Le ratio normalise : si un magasin vend 120% de sa moyenne le lundi, le ratio est 1.2. Cela rend la feature comparable entre magasins de tailles differentes.

Le module src/models/ implemente 7 modeles de prevision, tous conformes a l'interface BaseForecaster. Cela permet au backtesting de les evaluer de maniere uniforme.

Pourquoi passer le DataFrame complet plutot que X, y ? Prophet a besoin de la colonne date, le LSTM a besoin de store_id pour creer les sequences. En passant le DataFrame, chaque modele extrait ce dont il a besoin. Les modeles tabulaires (Ridge, RF, XGBoost, LightGBM) utilisent simplement df[feature_cols] et df[target_col].

Modele 1 : Seasonal Naive (baseline)

src/models/naive.py
class SeasonalNaive(BaseForecaster):
    name = "seasonal_naive"

    def fit(self, df_train, feature_cols, target_col):
        self.store_means_ = df_train.groupby("store_id")[target_col].mean()
        return self

    def predict(self, df_test, feature_cols):
        preds = df_test["sales_lag_7"].copy()           # ventes de la semaine derniere
        mask = preds.isna()
        preds[mask] = df_test.loc[mask, "store_id"].map(self.store_means_)
        return preds.fillna(self.store_means_.mean()).values

Le baseline le plus important. Tout modele qui ne bat pas le Seasonal Naive est inutile — il suffit de repeter les ventes du meme jour de la semaine precedente. Ce baseline est etonnamment competitif en retail grace a la forte saisonnalite hebdomadaire. Si un lag n'est pas disponible, on utilise la moyenne du magasin comme fallback.

Modele 6 : Prophet

src/models/prophet_model.py
class ProphetForecaster(BaseForecaster):
    name = "prophet"

    def fit(self, df_train, feature_cols, target_col):
        # Agreger les ventes par jour (moyenne de tous les magasins)
        daily = df_train.groupby("date").agg(
            y=(target_col, "mean"), promo=("promo", "mean")
        ).reset_index().rename(columns={"date": "ds"})

        # Multiplicateur par magasin pour distribuer les predictions
        global_mean = daily["y"].mean()
        self.store_mult_ = df_train.groupby("store_id")[target_col].mean() / global_mean

        self.model_ = Prophet(yearly_seasonality=True, weekly_seasonality=True)
        self.model_.add_regressor("promo")
        self.model_.fit(daily)

    def predict(self, df_test, feature_cols):
        # Predire au niveau global, puis multiplier par le facteur du magasin
        forecast = self.model_.predict(...)
        preds = forecast["yhat"] * df_test["store_id"].map(self.store_mult_)
        return preds.clip(lower=0).values

Strategie "aggregate + scale" — Fitter un Prophet par magasin (1115 modeles) serait trop lent pour le backtesting. On fit un seul modele sur la moyenne des ventes journalieres, puis on distribue les predictions a chaque magasin via un multiplicateur store_mult = ventes_moyennes_magasin / ventes_moyennes_globales.

Prophet decompose automatiquement la serie en tendance + saisonnalite hebdomadaire + saisonnalite annuelle + regresseurs. L'avantage : il gere nativement les jours feries et les changements de tendance (changepoints). L'inconvenient : il n'utilise pas nos features engineerees (lags, rolling).

class _LSTMNet(nn.Module):
    def __init__(self, n_features, hidden_size, n_layers, dropout=0.2):
        super().__init__()
        self.lstm = nn.LSTM(
            input_size=n_features,
            hidden_size=hidden_size,
            num_layers=n_layers,
            batch_first=True,
            dropout=dropout if n_layers > 1 else 0.0,
        )
        self.fc = nn.Linear(hidden_size, 1)

    def forward(self, x):
        out, _ = self.lstm(x)        # (batch, seq_len, hidden)
        return self.fc(out[:, -1, :])   # dernier timestep → prediction

Architecture LSTM a 2 couches — Le reseau prend en entree une sequence de 14 jours de features (shape: (batch, 14, n_features)) et predit les ventes du jour suivant. L'etat cache (hidden_size=64) capture les patterns temporels que les features statiques ne captent pas.

Creation des sequences — Pour chaque magasin, on fait glisser une fenetre de 14 jours sur l'historique. Chaque fenetre produit un exemple d'entrainement. Le nombre total de sequences peut etre tres grand (~800K pour 1115 magasins), donc on echantillonne a max_train_samples=200K.

Prediction — Pour les jours de test, on concatene les derniers jours d'entrainement comme contexte. Chaque prediction utilise les 14 jours precedents de features (qui peuvent inclure des jours d'entrainement pour les premiers jours de test).

Backtesting walk-forward

Le backtesting temporel simule le deploiement reel : on entraine sur le passe et on evalue sur le futur. Contrairement au split aleatoire (qui fuit de l'information temporelle), le walk-forward respecte l'ordre chronologique.

  |=============== TRAIN fold 1 ===============|--TEST 1--|
  |=================== TRAIN fold 2 ==================|--TEST 2--|

Le fold 0 a le moins de donnees d'entrainement, le fold 2 le plus. Le gap_days=1 simule le delai reel entre la derniere observation et la premiere prediction (on ne connait pas les ventes "d'aujourd'hui" au moment de predire).

4 metriques d'evaluation

src/evaluation/metrics.py
def mae(y_true, y_pred):                           # Erreur absolue moyenne
    return np.mean(np.abs(y_true - y_pred))

def rmse(y_true, y_pred):                          # Racine de l'erreur quadratique
    return np.sqrt(np.mean((y_true - y_pred) ** 2))

def wape(y_true, y_pred):                          # % d'erreur pondere
    return np.sum(np.abs(y_true - y_pred)) / np.sum(np.abs(y_true))

def forecast_bias(y_true, y_pred):                 # Biais directionnel
    return np.mean(y_pred - y_true) / np.mean(y_true)

Pourquoi 4 metriques et pas 1 ?

  • MAE — Erreur moyenne en unite de ventes. Facile a interpreter ("le modele se trompe en moyenne de X ventes").
  • RMSE — Penalise davantage les grosses erreurs. Si RMSE >> MAE, le modele a des erreurs tres variables (outliers).
  • WAPE — Pourcentage d'erreur pondere par le volume. Preferable au MAPE car il ne divise pas par zero et donne plus de poids aux gros magasins.
  • Bias — Direction de l'erreur. Un biais positif = le modele surestime. Un biais proche de 0 est ideal pour le reapprovisionnement (Phase 5).
